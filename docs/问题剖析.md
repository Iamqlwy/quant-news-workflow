## 1. search_kb 报错——空错误消息

### 日志

```
{ "status": "error", "message": "搜索失败：" }
```

冒号后面为空，说明 `str(e)` 是空字符串。

### 错误链路追踪

服务端返回非 2xx 且 body 为空时：

1. `resp.json()` 失败（非 JSON）-> `body = resp.text` = `""`
2. `_parse_error(status_code, "")` -> `QuantClientHTTPError(status_code, detail="")`
3. `Exception.__init__("")` -> `str(e)` = `""`
4. `err(f"搜索失败：{e}")` -> `"搜索失败："`

### 根因

服务端响应超时，网关返回 **空 body 的非 2xx 响应**（502/504）。

- 客户端 `httpx.AsyncClient` timeout = **5 秒**
- 服务端搜索在混合模式下并行执行 ES BM25 + PG 向量搜索
- 复杂查询（如 `"ST股 退市 连续涨停 风险警示"`）总耗时超过网关 timeout
- 网关返回 504/502、body 为空，FastAPI 应用层从未收到请求

### 防御缺失

`for r in result.items:` 没有对 `result.items` 做空值检查。如果服务端返回 `items: null` 而非 `items: []`，会抛 `TypeError`。当前服务端不会出现此情况，但防御缺失。

## 2. safe_extract_json 解析自然语言输出

### 日志

```
_safe_extract_json 解析失败 (text前100字符):
  考虑到HIMS为美股（非A股），触发器的价格监控条件不适合当前系统。所有操作已完成。
```

### 调用位置

`_run_deep_analysis()` 中 `data = _safe_extract_json(content)`（orchestrator.py:370）

### 根因

**Orchestrator 对 Agent 最终输出格式没有契约保证**。

- DeepAnalysis Agent 的 Stage 4 调用了 `create_trigger`
- `create_trigger` -> `TriggerCompiler.compile()` 编译失败（HIMS 是美股，A 股价格原子不适用）
- Agent 在最终输出中写了自然语言描述而非 JSON
- `_safe_extract_json` 试图从自然语言中提取 JSON，必然失败

### 实际影响

低。失败返回 `{}`，`data.get("reflection_days", 20)` 降级到默认值 20 天。

### 设计问题

`_run_deep_analysis` 用 Agent 的最终输出来解析 `reflection_days`，但 Agent 的 Prompt 中并没有要求最终输出必须包含 JSON。存在隐含的格式依赖关系但没有显式契约。

## 3. pydantic 校验错误——list 元素应为 dict 却收到 str

### 日志片段

```
6 validation errors for NodeStateCreate
primary_drivers.0
  Input should be a valid dictionary
  [type=dict_type, input_value="{'driver': '伊朗气田...', 'evidence_ids': ['R1']}", input_type=str]
```

### 错误链路

LLM 调用 `update_node_state(primary_drivers=[...])`

1. `_ensure_list()` — v 已是 list，直接返回，不对元素做递归处理
2. `_resolve_evidence_ids()` — `isinstance(item, dict)` == False（item 是 str），跳过
3. `NodeStateCreate()` — 期望 `list[dict]`，收到 `list[str]` -> pydantic ValidationError
4. `except Exception` -> 返回错误给 LLM

### 根因

**LLM 将 dict 序列化为 Python repr 格式字符串**（`"{'driver': '...'}"`）而非真正的 dict 对象。

三个层面的防御缺失：

1. **`_ensure_list`** — 只在顶层做 `json.loads` 兜底，不对 list 内的每个元素做递归解析。Python repr 格式无法通过 `json.loads`。

2. **`_resolve_evidence_ids`** — 检查 `isinstance(item, dict)`，遇到 str 就跳过，没有尝试 `ast.literal_eval` 将字符串解析回 dict。

3. **异常处理** — `except Exception` 只返回错误给 LLM，期望 LLM 自行修正，成功率不高。

### 实际影响

中高。`primary_drivers`、`risks`、`focus_points` 三个结构化字段都可能失败。如果是 DeepAnalysis Agent 的 Stage 4 调用，Agent 可能重试或放弃，导致节点状态更新不完整。

## 4. create_trade 没有对应的 risk_control

### 逻辑链路

`_handle_deep_analyzing()` 流程：

1. `_run_deep_analysis(task)` — Agent 可能创建 buy trade
2. `_collect_created_entities(task)` — trade_ids 写入 task
3. `_route_post_analysis(task)` — 判断是否是 buy
4. 是 buy -> `_run_risk_control(task)`，否则直接进 `REFLECTION_PENDING`

### 根因

`_route_post_analysis()`（orchestrator.py:379）的判断逻辑有两个漏洞：

**漏洞一：查询异常被静默吞掉**

`quant.trading.get(tid)` 是 HTTP 调用，可能因网络抖动或数据同步延迟失败。异常被 `except Exception` 捕获，只写一条 DEBUG 日志（默认不输出）。即使确实创建了 buy trade，也会被认为没有 buy -> 不走风控。

**漏洞二：`operation_type` 字段名可能不匹配**

`getattr(trade, "operation_type", "")` 返回空字符串 -> `has_buy` 保持 False。

### 实际影响

高。交易创建后未经过风控审核直接进入复盘等待，存在重大风控隐患。问题间歇性出现，取决于网络状况和数据同步时机。

## 5. 触发器初始化/编译失败

### 日志

```
创建触发器 | X 环境不支持 | 手动记录：3个月后阿里下一季财报时重新验证
```

### 调用链路

DeepAnalysis Agent Stage 4 -> `create_trigger` -> `TriggerCompiler.compile()` -> `_convert_names_to_codes()` -> `market.resolve_stock_ticker(name)`

### 根因

**非交易日或模拟环境下缺少行情数据，导致标的名称 -> 代码转换失败**。

`_convert_names_to_codes()` 依赖 `MarketDataProvider` 解析股票/指数名称为 ticker 代码。在非交易日：
- `resolve_stock_ticker()` 可能因缺少行情数据返回空
- `resolve_index_name()` 同理
- 编译器报错 -> `create_trigger` 返回错误 -> Agent 记录"环境不支持"

注意：`_ensure_compiler()` 中的 `TriggerCompiler.__init__` 只创建 LLM Provider，不加载行情数据。编译出错发生在工具调用时（运行时），而非初始化时。

## 6. macro_daily 图片未被模型关注

### 观察

Langfuse 显示图片 URL 正确展示，但模型输出没有提及任何行情信息。

### 图片注入方式

`MacroAgent._on_stage_start` 在 Stage 0 开始时注入：

```python
messages.append(HumanMessage(content=[
    {"type": "text", "text": "【四大指数 120 天日线同图】"},
    {"type": "image_url", "image_url": {"url": url, "detail": "auto"}},
]))
```

### 可能根因

**图片可能根本没有被传递给模型。** 三种可能性：

**可能 A：模型不支持多模态**

- 如果 `_macro_provider.create_chat_model` 返回纯文本模型
- LangChain 会静默忽略不支持的 `image_url` 消息类型
- 模型只看到文字

**可能 B：`detail: "auto"` 导致低分辨率**

- Provider 可能将 auto 降级为 low 分辨率
- K 线图上密集的蜡烛线和指标难以辨认

**可能 C：注意力分配不足**

- 上下文含宏观报告全文 + 历史摘要 + 系统指令，文字量远大于图片
- 模型倾向于关注文字内容

### 确认方式

在 Langfuse 中查看传递给模型的完整消息列表：
1. 确认 `image_url` 类型块是否保留在最终请求中
2. 确认使用的模型名称是否支持多模态
3. 尝试 `detail: "high"` 并观察效果

## 7. 其他问题简要说明

### 7.1 kbquant queue status 只有 ingested 和 consumed

这不是 bug。`ingested` 是初始状态，`consume_by_workflow` 是消费后状态。Pipeline 内部的 17 个细分状态在 Orchestrator 的 `Task` 表中维护，不会反映到服务端的 processing queue。服务端的 queue 只回答一条资讯是否已被消费。

### 7.2 性能问题（每小时 600 条）

设计上已使用 `asyncio.gather` 并发 + 每个 TaskState 独立 Semaphore + 全局信号量。问题是 DeepAnalysis Agent 运行时间远超其他阶段，且全局信号量会成为瓶颈。可通过增大 `agent_deep_analysis_concurrency` 配置缓解。

## 总结：问题根因分类

| 类别 | 涉及问题 | 核心原因 |
|------|---------|---------|
| 网关超时 | 问题 1 | 网关 timeout 小于客户端 timeout，空 body 透传无区分 |
| Agent 输出格式不契约 | 问题 2、3、5 | LLM 输出格式不稳定（JSON/自然语言/Python repr），代码假设 JSON 但无兜底 |
| 异常被静默吞掉 | 问题 4 | `except Exception: logger.debug()` 导致关键路径静默失败 |
| 外部依赖不稳定 | 问题 5 | 行情缺失时标的解析失败，无降级机制 |
| 多模态不兼容 | 问题 6 | 图片注入对模型能力有隐式依赖，无回退机制 |
| 防御性编程缺失 | 问题 1、3、4 | 空值检查、递归解析、查询降级等防御缺失 |
